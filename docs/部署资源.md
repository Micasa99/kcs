# KCS Beta 部署资源与 Stable 保护边界

- 状态：**Test-serving；canary proven；Stable promotion blocked**
- 适用范围：KCS Beta 开发环境
- 权威位置：本文件
- Last reviewed：2026-08-19

当前dated部署、canary与Stable快照见[`v2-beta-live-2026-08-19.md`](v2-beta-live-2026-08-19.md)。
本文只保存可长期执行的资源、隔离、发布和回滚边界，不复制image、UID、Job ref或即时配额使用量。

## 1. 目标

在不改变现有 KCS Stable 服务、入口、数据和资源身份的前提下，在同一个 Kubernetes 集群中增加一套可独立开发、升级、回滚和销毁的 KCS Beta。

Beta 只服务 ResearchCosmos Test。ResearchCosmos Main/Stable 继续访问现有 KCS Stable。Beta 验证通过只允许提升代码版本；不得自动部署 Stable，也不得把 Beta 数据同步回 Stable。

这里的“保护”是可审计的控制面、命名空间、身份、数据和资源预算隔离。Beta 与 Stable 共享 GPU 节点，因此不宣称物理零竞争；必须通过优先级、配额、并发和预算门禁把竞争限制在批准范围内。

## 2. 不可破坏的 Stable 不变量

任何 Beta 操作都必须同时满足以下条件：

1. 不修改、重建、重启或缩放 `researchcosmos-v2` 中的任何对象。
2. 不修改 Stable 的 Deployment、Service、Ingress、Secret、ConfigMap、PVC、DB 或公开 DNS。
3. 不复用 Stable ServiceAccount、RoleBinding、service token、TLS 私钥或 PVC。
4. 不把 ResearchCosmos Main/Stable 的 KCS endpoint、token、namespace、cluster ID 或 queue 指向 Beta。
5. 不在 Beta 脚本中应用 `deploy/v2/nvidia-device-plugin.yaml`、StorageClass、共享监控基础设施或其他既有集群级资源。
6. 不直接运行当前 `scripts/deploy_v2_control.sh` 部署 Beta。该脚本和基础清单硬编码 `researchcosmos-v2`，不是 Beta-safe。
7. 不允许 Beta Job 抢占 Stable；Stable 调度优先级必须高于 Beta。
8. 不允许 Beta API 或 workload 读取、挂载、列举或删除 Stable 的 Secret、PVC、Pod、Job、NetworkPolicy 或事件。
9. 不允许 Beta 与 Stable 共用数据库、双写、CDC 或反向同步。
10. 不因 Beta 验证成功而自动发布 Stable。

若部署 diff 中出现任何 Stable 对象变更，部署必须停止。

## 3. 拓扑与命名

| 维度 | Stable（保持现状） | Beta（新增） |

| API transport | Stable既有入口 | 私有port-forward + SSH tunnel；不发布Beta API公网Ingress |
| 客户端 | ResearchCosmos Main/Stable 与现有调用方 | 仅 ResearchCosmos Test |
| API Deployment | `kcs-v2-api` | `kcs-v2-beta-api` |
| API Service | `kcs-v2-api` | `kcs-v2-beta-api` |
| API PVC | `kcs-v2-api-state` | `kcs-v2-beta-api-state` |
| API ServiceAccount | `kcs-v2-api` | `kcs-v2-beta-api` |
| workload ServiceAccount | `kcs-v2-workload` | `kcs-v2-beta-workload` |
| namespace Role/Binding | `kcs-v2-api` | `kcs-v2-beta-api` |
| capacity ClusterRole/Binding | `kcs-v2-capacity-reader` | `kcs-v2-beta-capacity-reader` |
| native runtime ConfigMap | `kcs-v2-native-runtime-config` | `kcs-v2-beta-native-runtime-config` |
| API TLS Secret | `kcs-v2-tls` | `kcs-v2-beta-tls` |

| Model Gateway | Stable既有路径 | private HTTPS ingress + prefix middleware → ResearchCosmos Test relay |

所有 Beta 名称必须带 `beta`，只有明确列出的只读集群资源可以共享。

## 4. 资源清单

### 4.1 Beta 独占的 namespaced 资源

Beta overlay 必须创建并只管理以下资源：

- Namespace `researchcosmos-v2-beta`
- Deployment `kcs-v2-beta-api`，1 replica，`Recreate`
- Service `kcs-v2-beta-api`，ClusterIP，HTTPS 443
- PVC `kcs-v2-beta-api-state`，初始 1 GiB，独立于 Stable
- ServiceAccount `kcs-v2-beta-api`
- ServiceAccount `kcs-v2-beta-workload`，默认不挂载 API token
- Role/RoleBinding `kcs-v2-beta-api`
- ConfigMap `kcs-v2-beta-native-runtime-config`
- Secret `kcs-v2-beta-tls`
- Secret `kcs-v2-beta-service-token`
- Beta workload、project workspace 与 native gateway NetworkPolicy
- private model-gateway Ingress、prefix Middleware、relay Service/EndpointSlice
- ResourceQuota `kcs-v2-beta-quota`
- LimitRange `kcs-v2-beta-limits`

Secret 只能由部署机上的未跟踪文件或 secret manager 注入。Git 中不得出现 token、私钥、证书私钥、provider credential 或生产连接信息。

### 4.2 可以共享但不得由 Beta 重建的资源

- Kubernetes 集群和 CNI
- GPU 节点及标签 `researchcosmos.io/pool=gpu`
- StorageClass `local-path` 与 `kcs-workspace`
- NVIDIA device plugin
- `metrics.k8s.io`
- `kcs-monitoring` 中的 Prometheus/Alertmanager/DCGM 基础设施

Beta 可以增加带独立 label、rule 名称和 dashboard 的观测配置，但不得重新 apply 或 patch 共享监控基础资源。当前监控清单硬编码 Stable namespace，不能原样用于 Beta。

### 4.3 唯一允许新增的集群级资源

以下资源必须使用 Beta 独立名称，并经集群管理员 diff 审核：

- ClusterRole `kcs-v2-beta-capacity-reader`：只允许 `list` Nodes
- ClusterRoleBinding `kcs-v2-beta-capacity-reader`：只绑定 Beta API ServiceAccount
- PriorityClass `kcs-v2-beta-low`：建议 value `-1000`、`preemptionPolicy: Never`

上线前必须证明 Stable Pod 的有效 priority 高于 Beta。Beta 不得创建或修改 Stable PriorityClass。

## 5. 初始资源上限

以下数值是 Beta 的初始硬上限，不是容量承诺。提高任一上限都需要单独评审；观察不足时应降低而不是自动放宽。

| 资源 | 初始上限 |
| --- | ---: |
| 同时被请求的 NVIDIA GPU | 1 |
| 同时运行的 GPU Job | 1 |
| `count/jobs.batch` | 4 |
| Pods | 12 |
| PVCs | 8 |
| namespace 总 CPU requests | 8 cores |
| namespace 总 memory requests | 32 GiB |
| namespace 总 storage requests | 200 GiB |
| 单次 GPU Job wall time | 6 hours |
| API state PVC | 1 GiB |

Kubernetes ResourceQuota 至少同时约束 `requests.nvidia.com/gpu=1` 与 `limits.nvidia.com/gpu=1`。仅依赖 Job 数量不足以限制 GPU 竞争。

KCS admission还必须在创建Job前执行：

1. Beta GPU Job 已有一个时拒绝第二个。
2. 超过单Job wall-time上限时拒绝。
3. Stable 保留容量不足时拒绝 Beta；不得先创建再清理。
4. workload 必须使用 `kcs-v2-beta-low`。
5. 不允许 privileged、hostNetwork、hostPID、hostIPC、hostPath，或挂载 Stable Secret/PVC。

ResearchCosmos Test另外拥有自己的ResearchRun GPU预算，并在KCS mutation前做客户端
reservation/settlement。具体数值只维护在ResearchCosmos consumer config；它不是KCS owner fact，KCS不复制第二份ledger。

共享节点意味着短暂的 CPU、内存、I/O 干扰仍可能发生。配额、requests/limits、优先级和 canary 证据共同构成接受边界。

## 6. 网络与身份隔离

Beta API 的 Role 只能作用于 `researchcosmos-v2-beta`。ClusterRole 只允许读 Node capacity，不得读 Secret、PVC、Pod 或 Job。

每个新 Beta Attempt 必须在 Pod 创建前创建并读回 deterministic NetworkPolicy。`none` 与 `restricted` 都是 deny-by-default：

- 允许所需 DNS；
- 允许明确配置的 platform/model gateway CIDR 的 TCP 443；
- native lane 仅允许 KCS API 到 control sidecar 的规定端口；
- 其他 ingress/egress 拒绝；
- `restricted` 的外部数据访问只能经获批的 typed operation；
- 不允许把任意 shell/curl 公网访问称为 `restricted`。

NetworkPolicy object 的 observed attestation 只能证明 Kubernetes API 中存在匹配对象，不能单独证明 CNI dataplane 已执行。上线还必须有真实网络 canary。

Beta使用独立service token与TLS certificate/key。ResearchCosmos Test通过私有transport连接，仍以
`kcs-beta.ai-cosmos.cn`校验证书身份。ResearchCosmos Test的Beta token对Stable必须无效，Stable token
对Beta也必须无效。

## 7. 数据初始化与持续边界

Beta 可以从 Stable 做一次性脱敏快照初始化，但快照不是持续同步机制。

### 7.1 快照前提

1. 为 Stable 创建一致性备份；不得直接挂载或复制正在写入的 DB 文件。
2. 记录源版本、源 schema、备份时间和 SHA-256。
3. 在隔离目录中执行 sanitizer，不在 Stable PVC 上原地修改。
4. sanitizer 只保留获批的终态、非敏感开发样本。

### 7.2 必须排除或重置

- service tokens、TLS keys、provider credentials、Kubernetes Secrets
- 非终态 Jobs、Attempts、leases、reservations、active handles
- 未完成 cleanup、pending outbox、未确认 tombstone
- 用户隐私数据、未批准的输入输出内容和敏感日志
- Stable endpoint、namespace、cluster identity 和 workload owner identity
- 任何可使 Beta 继续控制 Stable resource 的 ref 或 credential

### 7.3 导入证据

导入包必须包含 sanitizer 版本、输入/输出 digest、各表保留/删除行数、敏感字段扫描结果和批准人。导入目标只能是新建的 Beta PVC。

导入后：

- Beta DB/PVC 独立演进；
- 不启用 CDC、双写或周期同步；
- 不把 Beta 结果写回 Stable；
- 再次刷新数据时必须销毁或备份旧 Beta 状态，重新执行完整流程。

无法证明脱敏的快照不得导入；可以改为空库启动。

## 8. Beta-safe 部署资产

当前独立overlay位于`deploy/v2/overlays/beta/`，专用入口为`scripts/deploy_v2_beta.sh`。它们必须满足：

1. 从基础模板生成 Beta namespaced 对象，但对所有名称、namespace、Secret、Service 和 Ingress 做显式替换。
2. 排除 device plugin、StorageClass、共享监控基础和 Stable cluster-scoped 对象。
3. 对 Beta ClusterRole/Binding/PriorityClass 使用独立名称。
4. 镜像只接受 `@sha256:` immutable digest。
5. 在 apply 前执行 render、schema validation、server-side dry-run 和 `kubectl diff`。
6. diff allowlist 只允许本文件列出的 Beta 对象；出现 `researchcosmos-v2` Stable 对象即失败。
7. 创建 Job 前已落实 ResourceQuota、LimitRange、RBAC 与 NetworkPolicy owner。

`scripts/deploy_v2_control.sh`和`deploy/v2/*.yaml`仍是Stable资产。不得通过字符串替换后直接远程执行来
冒充经过审计的Beta overlay。当前Beta脚本与native gateway policy的allowlist/object-count存在漂移，
因此只能维护live Test，不能作为下一次可重复发布入口；准确阻点见dated evidence。

## 9. 部署顺序

1. 记录 Stable 基线：对象 UID/resourceVersion、镜像 digest、replica、健康、队列、PVC 与 DB 备份。
2. 生成 Beta 全量 manifest，执行本地验证、server-side dry-run、`kubectl diff` 和 allowlist 检查。
3. 创建 Beta Namespace、ResourceQuota、LimitRange、PriorityClass、ServiceAccount 和 RBAC。
4. 创建独立 ConfigMap、token/TLS Secret；验证 token 交叉失效。
5. 创建 Beta PVC；如需要，导入已批准的脱敏快照。
6. 创建 namespaced NetworkPolicy。
7. 部署 Beta API Deployment 和 Service，等待健康。
8. 建立private API tunnel与private model-gateway ingress/relay；以`kcs-beta.ai-cosmos.cn`作TLS authority。
9. 运行 KCS 自检和真实 workload/network/GPU canary。
10. 再次确认 Stable 对象、Pod restart count、endpoint、队列和健康无变化。
11. 最后只切 ResearchCosmos Test；Main/Stable 不切流。

任一步失败都停止后续步骤。不得通过临时指向 Stable 来“兜底” Beta。

## 10. 上线验收

### 10.1 Stable 保护证据

- Stable Deployment/Service/Ingress/Secret/ConfigMap/PVC 的 UID 与配置未变化。
- Stable Pod 没有因 Beta 部署重启或 rollout。
- Stable endpoint、service token、namespace 和 client config 未变化。
- Stable 健康、队列延迟与 GPU 作业成功率未出现超出基线的回归。
- Beta ServiceAccount 无法读写 Stable namespace 的 namespaced resource。

### 10.2 Beta 功能与资源证据

- Beta 健康接口、contract fingerprint 与 immutable image digest 匹配。
- ResearchCosmos Test 能鉴权；Main/Stable 仍命中 Stable。
- 一个 1-GPU Beta Job 可运行；第二个并发 GPU Job在创建前被拒绝。
- Stable 调度需求出现时，Beta 不阻止 Stable 获得 GPU。
- `none`/`restricted` canary 中 DNS 与规定 gateway TLS 成功，任意公网 IP/域失败。
- `restricted` typed SourceAccess 成功，`none` 不具备 network-effect grant。
- Job/Pod/NetworkPolicy/PVC cleanup 后无跨 namespace 残留。
- inspect 只报告 observed NetworkPolicy，不宣称 CNI 已执行。

已完成的live证据与仍未完成的网络/调度矩阵见dated evidence。canary成功只允许标记
`Test-serving/canary proven`；在clean release、rollback和完整矩阵关闭前不得标记promotion ready。

## 11. 回滚与销毁

回滚顺序：

1. 先撤回 ResearchCosmos Test 的 Beta endpoint/token 配置。
2. 停止新的 Beta admission，等待或取消 Beta Job。
3. 将 Beta API scale 到 0；保留日志、DB/PVC snapshot 和对象证据供诊断。
4. 如为镜像回归，只把 Beta 回滚到上一 immutable digest。
5. 如为数据回归，只恢复 Beta PVC snapshot；不得触碰 Stable PVC。
6. 明确批准后，按 Ingress → Service/Deployment → workload/PVC → Secret/ConfigMap → RBAC → Namespace 的顺序销毁 Beta。
7. ClusterRole/Binding/PriorityClass 仅在确认无 Beta 对象引用后删除。

任何回滚/销毁命令的目标 namespace 必须显式为 `researchcosmos-v2-beta`。禁止使用未解析变量、宽泛 glob 或递归删除。

## 12. 版本提升规则

Beta 验证通过的产物是：

- 经 review 的代码提交；
- 新 KCS/OpenAPI 版本与 digest；
- migration 与 rollback 说明；
- canary、资源、网络和 Stable 不变量证据。

它不包含自动 Stable rollout。Stable 发布必须另行备份、审批、dry-run、维护窗口、canary 和回滚。Beta 数据不参与 Stable 发布。

## 13. Redeploy / promotion stop gates

当前完成/部分/未完成状态只见[dated evidence](v2-beta-live-2026-08-19.md)。任何重新部署或Stable
promotion都必须同时满足以下长期门禁：

- Beta overlay/render/schema/dry-run/diff allowlist从clean source可重复执行；
- API、platform、runtime recipe与adapter均有immutable digest及current/previous release manifest；
- certificate gate覆盖实际TLS authority，token双向隔离与Beta RBAC边界通过；
- quota、低优先级、单GPUadmission、CNI deny与Stable GPU demand共存有当前版本证据；
- CPU/GPU/gateway/capture/cleanup canary无owner orphan或未解释的managed resource；
- Beta API/runtime config/PVC与外部adapter完成rollback/restore演练；
- ResearchCosmos Test consumer release与KCS release exact绑定，Main/Stable配置和identity保持不变。

任何Stable promotion必须重新经过独立备份、审批、diff、canary和rollback门禁；不得把本次Test证据直接提升。
